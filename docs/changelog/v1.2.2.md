# v1.2.2 — Worker bug fix: Pro plan limit

**Released:** 2026-04-07  
**Scope:** Cloudflare Worker (server-side only — no app binary change)

---

## What changed

**Bug fix:** Pro users were shown a numeric request cap (`0 / 2.000 requests this month` or `0 / 30 requests this month`) instead of `Unlimited requests`.

**Root cause:** `PLAN_LIMITS["pro"]` is `null` (unlimited). JavaScript's `??` operator treats `null` as nullish, so `null ?? PLAN_LIMITS.free` evaluated to `30` — silently giving Pro users the free-plan ceiling. The `GET /account/usage` endpoint returned `"limit": 30` instead of `"limit": null`.

**Fix:** Replaced the `??` lookup with an `in`-operator ternary so that `null` is preserved:

```js
// Before
const limit = PLAN_LIMITS[row.subscription] ?? PLAN_LIMITS.free;

// After
const limit = row.subscription in PLAN_LIMITS ? PLAN_LIMITS[row.subscription] : PLAN_LIMITS.free;
```

Applied to both `POST /improve` (rate-gate) and `GET /account/usage` (usage response). See [ADR-039](../app/adr/039-worker-plan-limit-in-operator.md) for full rationale.

**UI fix (app):** The "resets May 1" reset-date label is now hidden for Pro users (unlimited), since a reset date is irrelevant when there is no cap.

---

## Impact

| Audience | Impact |
|----------|--------|
| Pro users | Account view now shows "Unlimited requests" with no progress bar or reset date |
| Free users | No change — still shows `N / 30 requests this month` with reset date |
| Founders | Redeploy the Cloudflare Worker; no app binary change required |

## Deployment

Redeploy the Worker only:

```bash
cd cloudflare
wrangler deploy
```

No database migration required. No Stripe changes required.
